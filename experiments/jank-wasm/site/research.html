Research

This fork shows that jank programs can be compiled ahead of time to WebAssembly and run in the browser with garbage collection on. The demos on the main page are the evidence: an unchanged official jank game and an interactive example, both built from the same source as their native binaries.

It is a proof of concept, not production support. This page describes how it works, where it is weak, and what would come next.

How it works

jank already compiles Clojure to C++. The fork builds that C++ and jank's runtime with Clang through Emscripten, then rewrites the linked module so the collector can see every live reference.

Garbage collection

jank uses Boehm GC (bdwgc), which finds live objects by scanning memory. On Wasm it can scan linear memory but not Wasm locals or the operand stack, and under Emscripten it registers no static data. Both gaps lose live objects.

  • Static data. Each app registers __global_base..__data_end with GC_add_roots before startup. Generated module loaders also register their lifted vars and constants. The gap was found by instrumenting startup: a reader-options map cached in a C++ static was collected and its memory reused.
  • Locals. Binaryen's --spill-pointers copies live pointer-width locals to the shadow stack around each call, where bdwgc scans them. It does not know which values are jank references; on wasm64 it spills every i64 that is live across a call. This is conservative, which suits a conservative collector. --flatten runs first so operand-stack values become locals. A small Binaryen patch makes the shadow stack 64-bit and restores it on exceptional exit.
  • Exceptions. C++ exception storage is not scanned. Thrown jank objects and errors are held in runtime-owned root cells through throw, rethrow and copied exception_ptrs.

Browser loop

The game keeps its blocking while (!WindowShouldClose()) loop. raylib's web build sleeps inside WindowShouldClose; the build links with JSPI so that call suspends to the browser and resumes on the next frame. A small C++ driver registers the static roots and wraps EndDrawing for stats. The live example instead returns to the browser after each chunk, and the driver collects there, on an empty stack.

Known gaps

  • Rooting is tested, not proven. Pointer-derived values held as i32 or f64 on wasm64 are not spilled, and no audit shows they are dead at every call that can collect.
  • Native C++ exceptions that hold GC-managed fields are not rooted.
  • Not tested: std::function captures, GC during a JSPI suspension, recursion deeper than 32 frames, long sessions.
  • wasm32 has not been run through the 14-case lifetime matrix.
  • Ahead of time only. No REPL, eval or threads.
  • emscripten::val through jank's C++ interop has not been tried. The demos use EM_ASM and Emscripten's C APIs.

Next steps

StepBlocker and work
Run jank's test suite under WasmThe suite runs through the native host. It needs a Node runner for the doctest and jank-file tests against the wasm64 build, with GC on. This is the most direct way to find rooting and platform bugs, and the first thing to do.
Remove the spill costThe spill pass cannot tell jank references from integers. The compiler knows which values are references, so it can keep its own root frames or emit typed arithmetic that holds no references, and the spill pass is no longer needed. Collection kernels also need runtime work: chunked ranges, fewer copies in sort and string building.
Package one Wasm commandjank-build works but needs Docker, a patched Binaryen, downloaded Emscripten and Node, and per-app root drivers. A real jank target would ship the runtime archive, apply the pass and register roots itself.
Measure sizeAttribute module size by component, then try LTO and wasm-opt dead-code removal.
